# InsureTech — анализ проблем и рисков текущей архитектуры

## 1. Описание текущей архитектуры взаимодействий

**Сервисы:**

- **`core-app`** — основной бэкенд для клиентов.  
  Хранит локальную реплику тарифов и продуктов, получаемую от `ins-product-aggregator` каждые **15 минут**.
- **`ins-comp-settlement`** — сервис взаиморасчётов со страховыми компаниями.  
  Раз в сутки:
  - получает тарифы от `ins-product-aggregator`;
  - делает REST-запрос к `core-app` для получения оформленных за день страховок.
- **`ins-product-aggregator`** — сервис интеграции со страховыми компаниями.  
  При каждом вызове:
  - синхронно запрашивает данные от **5 внешних страховых компаний**;
  - агрегирует ответы и возвращает единый список.

## 2. Проблемы и риски при росте нагрузки

| № | Проблема | Описание | Последствие / Риск |
|:-:|-----------|-----------|--------------------|
| **1** | Синхронные вызовы `ins-product-aggregator` | При каждом REST-запросе aggregator блокирующе опрашивает внешние API | Рост числа партнёров (до 10+) приведёт к росту времени ответа и таймаутам |
| **2** | Дублирующие запросы | `core-app` опрашивает aggregator каждые 15 мин, `settlement` — раз в сутки | Избыточная нагрузка на aggregator и внешние API, риск превышения лимитов запросов |
| **3** | Монолитная агрегация без кэширования | aggregator ждёт ответ от всех API, прежде чем вернуть результат | Один медленный партнёр блокирует ответ, снижая доступность |
| **4** | Отсутствие изоляции ошибок внешних API | Ошибка одной компании может вызвать сбой всего запроса | Потеря данных, SLA-нарушения, нестабильность сервиса |
| **5** | Дублирование тарифных данных | Разные версии тарифов в `core-app` и `settlement` | Нарушение консистентности и ошибки при расчётах |
| **6** | Пакетное обновление тарифов | Обновления происходят по расписанию (раз в 15 мин / сутки) | Данные устаревают, пользователи видят неактуальные тарифы |
| **7** | Масштабирование числа партнёров | При добавлении новых страховых компаний нагрузка возрастает линейно | Возможна деградация производительности и рост времени ответа |
| **8** | Отсутствие очередей и буферов | Все операции выполняются синхронно | Нет ретраев, невозможна асинхронная консолидация данных |
| **9** | Недостаточная наблюдаемость процессов | Нет информации о времени получения и актуальности тарифов | Сложности в аудите и контроле SLA с партнёрами |
| **10** | Ограниченная масштабируемость `ins-product-aggregator` | Каждый экземпляр делает полные внешние запросы | Горизонтальное масштабирование неэффективно, нагрузка растёт нелинейно |

---

## 3. Итоговое резюме

Текущая архитектура InsureTech **чувствительна к росту числа партнёров и увеличению объёмов данных**.  
Синхронные REST-взаимодействия и отсутствие буферизации приводят к:

- увеличению времени отклика и частым таймаутам;  
- потере данных при сбоях внешних API;  
- несогласованности между микросервисами;  
- риску нарушения SLA и ухудшению клиентского опыта.

Без пересмотра модели интеграции система не сможет масштабироваться при добавлении новых страховых компаний и росте клиентской нагрузки.
